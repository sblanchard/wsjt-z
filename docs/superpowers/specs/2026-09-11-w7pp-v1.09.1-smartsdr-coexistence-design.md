## SmartSDR coexistence mode

v1.05.8 had one ownership model: WSJT registers itself as a FLEX **GUI
client** (`client gui`), so the slice it creates and every stream it opens
belong to its own client handle. That is the headless path this fork
runs on the air today.

v1.09.1 adds a second path, chosen at connect time:

1. `sub client all` — read-only. If a `client ... connected ...
   program=SmartSDR-Win` status line arrives, SmartSDR is present and its
   `client_id=` is captured.
2. **SmartSDR absent** → the headless path, unchanged.
3. **SmartSDR present** → WSJT stays a non-GUI API client and:
   - `client bind client_id=<SmartSDR's id>` — attaches to the running
     SmartSDR GUI client instead of competing with it for a GUI slot.
   - `sub slice all` while a *snapshot* gate is open: every in-use slice
     number is recorded, and the one reporting `tx=1` is remembered as
     `previous_tx_slice_id_`.
   - `slice create mode=digu` while a *create* gate is open: the first
     in-use slice whose number is **not** in the snapshot is WSJT's. The
     radio assigns that slice to SmartSDR's GUI handle, so ownership by
     handle cannot identify it — only the new number can. The slice's
     `pan=0x...` is remembered so the extra panadapter SmartSDR grows can
     be removed at shutdown.
   - The slice is **not** made the TX slice at startup. `slice s <n> tx=1
     mode=digu` (and a re-send of the last RF power level) happens on PTT
     on, and the previously transmitting slice is restored on PTT off and
     on shutdown. SmartSDR's operator keeps their TX slice between WSJT
     transmissions.
4. Both paths: after the DAX-TX stream is captured, `stream set 0x<id>
   tx=1` explicitly selects this client's stream as the radio's TX sample
   source (FlexLib's `DAXTXAudioStream.IsTransmitChannel`). Shutdown sends
   `stream remove 0x<id>`.
5. DAX-TX stream capture now matches on the stream's own `client_handle=`
   field — this fork's earlier `DEVIATION` guard, adopted upstream.

`client gui` is now sent through `send_command()` like every other
command, so the sequence counter starts at 1.

## Decisions for this fork

- **Port coexistence close to verbatim.** The README promises the W7PP
  code is carried diffable against future releases; that is exactly what
  made this roll-in a mechanical diff. Keep W7PP's structure and markers;
  mark every intentional difference `DEVIATION from W7PP`.
- **Keep this fork's `wait_for_owned_slice()`** in both paths. Upstream
  re-issues `sub slice all` once if the create response beats the slice
  status; the wait loop already handles that race and the create gate
  simply stays open for the duration of the wait.
- **Keep this fork's `slice s <n> dax=<ch>` routing** in both paths. In
  coexistence it moves the DAX channel onto WSJT's new slice, which is
  what the RX bridge needs.
- **Thread-safe TX route hand-off.** `NativeFlexTransceiver` runs on
  Configuration's transceiver thread and `SoundOutput` on the audio
  thread; dynamic `QObject` properties are not thread-safe. Publish and
  read them on `QCoreApplication`'s thread as upstream now does. Publish
  after connect with `Qt::BlockingQueuedConnection` (upstream); clear on
  stop with `Qt::QueuedConnection` — never block the transceiver thread
  on the main thread during shutdown, when the main thread may be waiting
  on the transceiver thread.
- **Drop the three debug files** (TX status evidence, offline VITA dump,
  TX PCM capture) as upstream did. They were release-engineering
  scaffolding; the `W7PPNativeFlexTxCapture` application property stays,
  because upstream still uses it as the "Native FLEX is the active rig"
  flag in `SoundOutput`.
- **Copyright banners** are added to the files this roll-in touches; the
  rest of the W7PP files pick them up on the next roll-in.
- **Test with a fake radio.** `do_start()` / `do_stop()` are exercised
  against a scripted loopback SmartSDR TCP endpoint in both modes, with
  the transceiver on a worker thread as in production. PTT is not
  covered: its safety gate needs live meter telemetry.
- **Any GUI client triggers coexistence, not only `SmartSDR-Win`**
  (operator's request, 2026-09-11). The donor only ever knew SmartSDR for
  Windows, but this operator drives the radio from SmartSDR for Mac, and
  other GUI clients (AetherSDR, ...) exist. The discriminator is therefore
  a `client ... connected` status line carrying a **non-empty
  `client_id=`** field, in both `capture_smart_sdr_client()` and the RX
  bridge's `smartSdrGuiPresent` guard: the radio reports a `client_id`
  only for clients that registered with `client gui`, so every GUI flavour
  matches while API-only clients — this fork's own CAT, RX bridge and
  safety-monitor connections included — never do. The program name is no
  longer consulted. Consequence: a client line without a `client_id` is
  simply not a GUI client, so the headless path runs; the "found SmartSDR
  but received no SmartSDR client_id" throw is kept as a defensive check
  but is unreachable in practice.

## Not changed

- `NativeFlexSafetyMonitor`, `NativeFlexRadioSelection`, discovery, the
  radio dialog, `FlexBandLevels`, `BandSettleGate`: upstream changes are
  banner-only or absent.
- The RX bridge (`FlexVitaReceiver`) keeps its own API connection; in
  coexistence mode its DAX RX stream is still owned by that connection's
  handle, so its ownership guard is unaffected.
